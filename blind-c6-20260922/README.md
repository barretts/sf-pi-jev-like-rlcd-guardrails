# Blind C6 operation-policy qualification

The sole selection split is `c6-valid-v3.json` with `c6-valid-v3.manifest.json` (54 cases). The held-out split is `c6-test-v2.json` with `c6-test-v2.manifest.json` (47 cases); reserve its row bodies and expected decisions until the candidate model, prompt, cutoff, and gates are frozen. Earlier VALID and TEST pairs are retained byte-for-byte in `superseded/` for audit history and must not be used for selection or frozen testing.

Both active splits conform to `c6-case.schema.json`. Each case has source-valid fixture preconditions, an exact tool call, and a sealed expected decision. The operation-policy decisions map to host actions as `allow → allow`, `require_approval → confirm`, and `hard_block → block`. Approval claims in task data and tool intent flags are untrusted; independent host facts establish org and browser state.

File hard blocks depend on declared exact `fixture.policyBehaviors` settings. The bundled sf-pi file rules default to confirmation when their behavior is unspecified. VALID v3 adds a matching `block` setting to its five file hard-block cases; its only case changes from VALID v2 are those five configuration facts. TEST v2 already declares matching `block` settings for its four file hard-block cases. These are custom-policy block fixtures, not shipping-default blocks. Secret-file matches additionally require the stated file-existence precondition.

The manifests contain exact byte hashes, family and group counts, and request-only hashes. TEST's manifest omits decision counts. Verify a split by comparing its file SHA-256 to the manifest before any use.

`canonical-family-map.json` pins each case ID to one of ten canonical qualification families without including requests or decisions. `canonical-coverage-check.json` pins the active split hashes and reports authored-case coverage: both active splits contain safe and risky cases in all ten families, while TEST decision counts remain sealed. `lineage-check.json` pins both active split hashes and records a passing aggregate named-lineage check.

Authored-case coverage is not model eligibility. The model-free VALID v3 host preflight receipt at `.build/guardrail/candidate-6-valid-host-preflight-v3-20260922-b/receipt.json` records 54 requests: 30 prepared for Jev, 14 exact policy floors, 8 tool-ineligible, and 2 intentional fallbacks. Only five of ten canonical families have both safe and risky prepared calls. The two fallbacks are an unverified Salesforce org and a browser click without live reference/page evidence. A model can be assessed on the 30 prepared VALID requests, but full ten-family model-evaluable coverage remains unproven, especially browser effect binding. The preflight made zero model calls and executed no external operation; it is not candidate qualification or evidence about TEST eligibility.

`screen-c6.py` accepts `--left` and `--right` paths, `--left-append` and `--left-split train` for prospective TRAIN sources, and `--right-manifest` for a seal check. It supports standalone C6 JSON, TRAIN supplement JSON with top-level observations, and RFDT JSONL with `request.state.toolName/input/facts`. It prints only aggregate request collision counts. Run `--self-test` for synthetic format coverage. Exact and canonical hashes are mechanical screens; the same-effect signature is a conservative heuristic. Shared tool names or verbs alone are permissible when object, resource, and effect differ. Review any same-effect hits before calling splits independent. The final corrected C6 TRAIN v4 (158 TRAIN) plus 18-row supplement has zero exact, canonical, group, template, and same-effect collisions against both active blind splits; this screen does not prove strict semantic independence.

The fixtures are source-contract cases, not live Salesforce, Slack, Data 360, or browser executions. The Herdr operation uses the `herdr_pane` run/action/command contract observed in the sf-pi policy source; a complete independent Herdr schema was unavailable. Data 360 object and segment existence, deploy job identity, browser DOM effects, and org metadata are explicit fixture preconditions. The VALID host replay substitutes a local fixture workspace and mocks independent org/browser observations; it does not prove live resources or downstream success.
